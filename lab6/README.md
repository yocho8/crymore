# Лабораторная работа 6: экспериментальная оценка производительности ОС

Этот комплект содержит готовую реализацию для двух групп экспериментов:

1. CPU-bound: вычислительно сложная задача, почти не использующая диск.
2. I/O-bound: обработка отдельных файлов с чтением чисел, умножением на 2 и немедленным дописыванием результата в конец того же файла.

Для каждой группы есть последовательный и параллельный запуск. Эксперименты нужно выполнить два раза: при 1 CPU и при 2 CPU в настройках виртуальной машины.

## 1. Подготовка

Установить зависимости:

```bash
sudo apt update
sudo apt install -y build-essential python3 python3-matplotlib time
```

Собрать C-программы:

```bash
make
```

Сохранить параметры системы:

```bash
./scripts/collect_system_info.sh > results/system_info_1cpu.txt
```

После переключения виртуальной машины на 2 CPU выполнить еще раз:

```bash
./scripts/collect_system_info.sh > results/system_info_2cpu.txt
```

## 2. Калибровка CPU-задачи

CPU-задача запускается так:

```bash
/usr/bin/time -f "%e" ./bin/cpu_task 1 80000000
```

Нужно подобрать такое значение итераций, чтобы один запуск занимал примерно 2-3 секунды.
Например:

```bash
/usr/bin/time -f "%e" ./bin/cpu_task 1 50000000
/usr/bin/time -f "%e" ./bin/cpu_task 1 80000000
/usr/bin/time -f "%e" ./bin/cpu_task 1 120000000
```

Выбранное значение передается через переменную `CPU_ITERS`.

## 3. Калибровка I/O-задачи

Сначала создать базовые файлы:

```bash
./scripts/prepare_io_data.sh 20 400000
```

Затем проверить время обработки одного файла:

```bash
./scripts/reset_io_work.sh 1
/usr/bin/time -f "%e" ./bin/io_task work/file_1.txt
```

Если получилось сильно меньше 2 секунд, увеличить второе число в `prepare_io_data.sh`, например до `700000` или `1000000`.
Если получилось слишком долго, уменьшить его.

## 4. Запуск экспериментов при 1 CPU

В настройках виртуальной машины поставить 1 процессор, загрузить ОС, собрать проект и выполнить:

```bash
CPU_ITERS=80000000 MAX_N=20 REPS=10 ./scripts/benchmark.sh cpu seq 1cpu
CPU_ITERS=80000000 MAX_N=20 REPS=10 ./scripts/benchmark.sh cpu par 1cpu

./scripts/prepare_io_data.sh 20 400000
MAX_N=20 REPS=10 ./scripts/benchmark.sh io seq 1cpu
MAX_N=20 REPS=10 ./scripts/benchmark.sh io par 1cpu
```

Заменить `80000000` и `400000` на значения, которые получились при калибровке.

## 5. Запуск экспериментов при 2 CPU

Выключить виртуальную машину, поставить 2 процессора, загрузить ОС и выполнить:

```bash
./scripts/collect_system_info.sh > results/system_info_2cpu.txt

CPU_ITERS=80000000 MAX_N=20 REPS=10 ./scripts/benchmark.sh cpu seq 2cpu
CPU_ITERS=80000000 MAX_N=20 REPS=10 ./scripts/benchmark.sh cpu par 2cpu

./scripts/prepare_io_data.sh 20 400000
MAX_N=20 REPS=10 ./scripts/benchmark.sh io seq 2cpu
MAX_N=20 REPS=10 ./scripts/benchmark.sh io par 2cpu
```

## 6. Построение графиков

После всех запусков:

```bash
python3 ./scripts/plot_results.py
```

Будут созданы:

- `results/*.csv` - сырые измерения;
- `results/summary.csv` - средние значения и стандартные отклонения;
- `plots/*.png` - графики для отчета.

В отчет вставить:

3. Описание CPU-алгоритма из `src/cpu_task.c`.
4. Описание I/O-алгоритма из `src/io_task.c`.
5. План эксперимента.
6. 8 графиков:
   - CPU, sequential, 1 CPU;

   - I/O, sequential, 1 CPU;

   - I/O, sequential, 2 CPU;

7. Выводы по CPU-bound и I/O-bound экспериментам.

## 8. Ожидаемая логика результатов

CPU-bound, 1 CPU:
- последовательный режим почти линейно растет с N;
- параллельный режим обычно не ускоряется, потому что все процессы конкурируют за одно ядро;
- из-за переключений контекста параллельный режим может быть даже медленнее.

CPU-bound, 2 CPU:
- последовательный режим почти такой же, как при 1 CPU, потому что задачи все равно выполняются одна за другой;
- параллельный режим должен быть быстрее, особенно пока N не сильно больше числа CPU;
- при большом N ускорение ограничивается числом ядер и накладными расходами планировщика.

I/O-bound:
- параллельный запуск может не дать хорошего ускорения, потому что процессы конкурируют за одну дисковую подсистему;
- при HDD возможны сильные просадки из-за перемещений головки и случайного доступа;
- при SSD графики могут быть ровнее, но параллельность все равно ограничивается пропускной способностью и очередью запросов ввода-вывода.
